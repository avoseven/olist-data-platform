# データ分析の進め方

このプロジェクトに限らず、データ分析で通る段階と、各段階で自分に問うことをまとめたもの。
各段階に「このプロジェクトでの例」を付けている。詳しい経緯は [分析の読み方ガイド](analysis_guide/README.md) と [dbt の読み方ガイド](dbt_guide/README.md) を参照。

## 全体の流れ

```
0. 問いを決める          何を知りたいか、何のためか、何はやらないか
1. データを知る          粒度、キー、つながり、欠損、期間
2. 分析用のデータを作る   粒度をそろえる、二重計上を防ぐ、テストする
3. 指標を定義する        単位、分母、NULL、同数のとき
4. 探索する              分布、偏り、相関、欠損の偏り
5. 分ける / モデルを作る  ルールか手法か。指標だけでなく中身を見る
6. 比べる                単位、分母、交絡、観察期間、偶然の揺れ、差の大きさ
7. まとめる              事実・解釈・仮説、制約、検証の設計
```

**一直線には進まない**。5 で結果がおかしければ 3 や 4 に戻り、6 で定義の問題が見つかれば 3 に戻る。
このプロジェクトでも、K-means を 2 回試してからルールに切り替え (5 → 0 に戻って目的を決め直した)、再購入の分析中にリピーターの定義を直した (6 → 3)。
戻ること自体は失敗ではない。**戻った理由を記録しておく**ことが大事。

## 0. 問いを決める

| 自分に問うこと | このプロジェクトでの例 |
|---|---|
| 何を知りたいか。1 文で書けるか | 顧客の購買傾向と購入体験を理解し、改善機会を探る |
| 結果を誰が、何に使うか | 販促の対象選び、施策の仮説 |
| このデータで**答えられないこと**は何か | 施策の効果 (実施したあとのデータがない) → 対象外と明記 |
| 「分かった」と言える状態はどういうものか | セグメントごとの違いを、事実・解釈・仮説に分けて示せる |

最初の問いは大まかでよい。ただし、**答えられないことは最初に書いておく**。書いておかないと、最後に言い過ぎる。

このプロジェクトでは、目的 ([ADR 011](decisions/011_segmentation_purpose_and_roles.md)) を決めたのは K-means を試したあとだった。手法を試す前に目的が決まっていれば、遠回りは短くなった可能性がある。

## 1. データを知る

| 自分に問うこと | このプロジェクトでの例 |
|---|---|
| 各テーブルの 1 行は何か (粒度) | `orders` は 1 行 = 1 注文、`order_items` は 1 行 = 注文の明細 1 行 |
| 主キーは本当に一意か | `order_reviews` に 2 種類の重複があった ([notebook 01](../notebooks/01_order_reviews_duplicates.ipynb)) |
| テーブルどうしは、どの列でつながるか。つながらない行はあるか | [src/check_relationships.py](../src/check_relationships.py) |
| 「人」を数える列はどれか | `customer_id` は注文ごとに発行される。人は `customer_unique_id` で数える |
| 欠損・不整合はどこにあるか | 配達日時の欠損、日時の順序の逆転 ([data_notes.md](data_notes.md)) |
| データの期間は。終わりの近くに偏りはないか | 2018-08-29 で終わる。最近の注文は配送の早いものに偏る |
| 使わないテーブルはどれか、なぜか | `sellers`・`geolocation` ([ADR 001](decisions/001_table_selection.md)) |

ここで分かったことは、仕様のメモ ([data_notes.md](data_notes.md) のようなもの) に書いておく。あとの段階で何度も参照する。

## 2. 分析用のデータを作る

| 自分に問うこと | このプロジェクトでの例 |
|---|---|
| 分析の単位は何か (1 行 = 何にするか) | 1 行 = 1 人 (`customer_features`) |
| 粒度の違う表を結合して、行が増えないか (二重計上) | 明細と支払いは、先に注文単位に集約してから結合する ([dbt ガイド 3 章](dbt_guide/03_order_mart.md)) |
| 対象の行の条件は何か | delivered の注文だけ ([ADR 006](decisions/006_mart_design.md)) |
| 作った値が正しいことを、どう確かめるか | 合計の突き合わせ、別の書き方での再計算 ([dbt ガイド 5 章](dbt_guide/05_tests.md)) |
| 手法に依存する加工は、どこでするか | 対数変換・標準化は notebook。mart には加工前の値 |

SQL を使わない場合 (pandas だけの場合) でも、粒度・二重計上・突き合わせの考え方は同じ。

## 3. 指標を定義する

| 自分に問うこと | このプロジェクトでの例 |
|---|---|
| 平均や割合は、何を 1 件として数えるか | 注文ごとの値の平均か、レコードの平均か、合計どうしの比か ([ADR 007](decisions/007_customer_feature_principles.md) 原則 2) |
| 分母は何か | レビューの平均は「レビューがある注文」、投稿率は「すべての注文」 |
| NULL はどう扱うか。0 と NULL を区別しているか | カテゴリが分からない商品しかなければ、カテゴリ数は 0 ではなく NULL |
| 1 つを選ぶとき、同数ならどうするか | 辞書順など固定のルールで決め、何度実行しても同じにする |
| 同じ列が、人によって違う意味にならないか | 合計金額は、リピーターには複数回の合計 → 単発購入の顧客だけを金額で区切る |
| 定義は、言いたいことと合っているか | 「注文 2 件以上」では、同じ日に注文が分かれただけの人もリピーターになる → 「異なる購入日が 2 つ以上」に直した ([ADR 013](decisions/013_repeat_customer_definition.md)) |

**定義を決めることと、使うことを分ける**。先に定義を決めて作っておけば、使わなかった指標も解釈に使える。

## 4. 探索する

| 自分に問うこと | 見るもの |
|---|---|
| NULL はどれくらいあるか | `isna().mean()` |
| ほとんど全員が同じ値ではないか | 最も多い値の割合 |
| 偏りや外れ値はどれくらいか | 歪度、中央値、99% 点、最大値。ヒストグラム (偏りが大きければ対数でも) |
| 似た情報を持つ指標はないか | 順位相関 (偏りや外れ値があるとき)。相関が高い理由を、データの構造で説明できるか |
| 欠損はランダムか | 欠損がある人とない人で、ほかの指標を比べる。比べる列は、欠損の理由の仮説 (時間 / 記録の仕組み / 人の行動 / 対象の違い) から選び、全体はあとで眺める ([分析ガイド 1 章](analysis_guide/01_feature_selection.md)) |
| データ全体に効いている構造は何か | このプロジェクトでは「97% が 1 回しか買っていない」 |

**見る前に、何を見て何を判断するかを書く**。見てから理由を探すと、都合のよい解釈になりやすい。

## 5. 分ける / モデルを作る

| 自分に問うこと | このプロジェクトでの例 |
|---|---|
| 条件を書けば分けられるものはないか | リピーター、遅延経験者 → ルール (フラグ) で分ける |
| 手法の前提に合っているか | K-means は距離を使う → 単位をそろえる (標準化)、0 / 1 の列は少数派が強調される |
| 手法の設定は足りているか | `n_init=10` では結果がシードで変わった → 50 に増やした |
| 評価の指標だけで判断していないか | シルエット係数が最も高い k = 3 は、少数派が切り出されただけだった |
| 何で分かれたかを説明できるか | クラスタごとの加工前の値、R²、条件とのクロス集計 |
| そもそも、自然なまとまりはあるか | 2 次元の分布に塊がなかった → K-means は分布を区切っただけ |
| ルールで作れる結果ではないか | 得られたクラスタは「高い / 低い」の組み合わせ → ルールにした |
| 区切り方に自然な境目はあるか | 細かく区切って (20 等分) 指標の変化を見る → 段差なし → 説明しやすい値 (50 / 150) |

**分けたら、まず中身を見る**。指標の数字が良くても、何で分かれたかを説明できなければ、使えない。

## 6. 比べる

ここが最も間違えやすい。比べる前に、次を確かめる。

| 自分に問うこと | 間違えるとどうなるか | このプロジェクトでの例 |
|---|---|---|
| 何を 1 件として数えるか (顧客か、注文か) | 結論が逆になる | リピーター: 遅延経験者の割合は最も高い (10.6%) が、注文の遅延率は最も低い (5.3%) |
| 分類に使った指標で比べていないか | 分けた条件を確かめるだけになる | 遅延は分類の条件にせず、比べる指標にした |
| 分母は何か | 違う指標を同じものとして比べる | 分母を指標ごとに書く |
| 比べる 2 つの両方に関係する要因 (交絡因子) はないか | 見かけの差を、原因と取り違える | 購入時期 → 時期の構成を比べる、時期ごとに比べる、直接法で調整する |
| 観察できる期間は、全員同じか | 最近の人ほど「まだしていない」だけなのに「しない」と数える | 90 日を観察できる顧客だけで再購入率を計算 |
| 差は偶然の揺れではないか | 人数の少ないグループの差を、本物の差と取り違える | 信頼区間を出す。人数の少ないカテゴリはまとめる |
| 差は、どれくらい大きいか | 小さな差に大きな施策をかける | 遅延をなくしても、全体の再購入率は 1.30% → 約 1.32% |
| 決め方を変えても、結論は同じか | 偶然の選択に左右された結論を出す | 複数カテゴリの顧客を除く、観察期間を変える |

## 7. まとめる

| 自分に問うこと | このプロジェクトでの例 |
|---|---|
| 事実・解釈・仮説を分けて書いているか | report の各節を 3 つに分けている |
| 解釈に、別の説明はありえないか | 「良い体験をしたからリピートした」のか「リピーターだから良い体験をした」のか、区別できない |
| どの数字は信頼でき、どの数字は条件で変わるか | 「同じカテゴリの方が早い」は安定、日数の値は観察期間で変わる → 傾向を根拠にする |
| 制約 (このデータで言えないこと) を書いたか | report 8 章 |
| 仮説を、どう検証するか | A/B テストの設計 (report 7.5) |
| 最初の問いに答えているか | 0 で書いた問いと照らし合わせる |

## 一人で進めるときのコツ

道筋を誰かに示してもらう代わりに、自分で道筋を作るための習慣。

### 各段階の始めに、4 つを書く

notebook の冒頭や、作業用のメモに、手を動かす前に書く。

```
問い:        この段階で何に答えるか
見るもの:    どの表・どの指標・どのグラフを見るか
判断の基準:  何がどうなっていたら、どう判断するか
気になる点:  起きそうな問題 (前の段階からの申し送り)
```

このプロジェクトの notebook は、どれも冒頭に「目的」「確認すること」があり、末尾に「まとめ」「次に確認すること」がある。
[ADR 008](decisions/008_feature_selection.md) の「次の段階で確認すること」は、notebook 03 で実際に起きた問題 (0 / 1 の特徴量が効きすぎる) を予告していた。**書いておくと、次に何を見るかが決まる**。

### 判断したら、短く記録する

ADR ほど正式でなくてよい。次の 4 つがあれば、あとで「なぜこうしたのか」を説明できる。

```
決めたこと
比べた候補
選んだ理由
見直す条件 (どうなったら、この判断を変えるか)
```

「見直す条件」を書いておくと、戻るべきタイミングが分かる。実際、[ADR 012](decisions/012_segment_definition.md) のリピーターの定義は、[ADR 013](decisions/013_repeat_customer_definition.md) で見直された。

### 期待する数を先に書いて、確かめる

```python
assert target.sum() == 84_354
```

人数を絞る、結合する、などの処理のあとに、期待する件数を `assert` で確かめる。合わなければ、そこで止まる。間違いに早く気づける。

### 結果が出たら、すぐ中身を見る

- 平均だけでなく、中央値や分布も見る
- 全体の数字だけでなく、グループごと・時期ごとに分けて見る
- 「何で分かれたか」「なぜこの値になったか」を、1 文で説明してみる。説明できなければ、まだ分かっていない

### 迷ったら、候補を並べる

「どちらが正しいか」で悩むより、候補を表に並べて、同じ観点で比べる。このプロジェクトでは、NULL の扱い ([ADR 009](decisions/009_clustering_preprocessing.md))、配送の指標 ([ADR 008](decisions/008_feature_selection.md))、金額の区切り方 ([ADR 012](decisions/012_segment_definition.md)) をすべてこの方法で決めている。

### おかしいと思ったら、手法より先にデータを疑う

K-means の結果がおかしかったとき、パラメータの調整に進まず、「入力にどんな特徴量が混ざっているか」を見直した ([ADR 010](decisions/010_rule_flags_and_clustering_scope.md))。
結果が期待と違うときは、多くの場合、手法の細かい設定より、データの構造や定義に理由がある。
