# 1. 特徴量の選定

[ADR 007](../decisions/007_customer_feature_principles.md)、[ADR 008](../decisions/008_feature_selection.md)、[notebooks/02_feature_selection.ipynb](../../notebooks/02_feature_selection.ipynb) を見る。
`customer_features` の列のうち、K-means に入れる特徴量を選ぶ段階。

## この段階の役割

`customer_features` には 22 列ある。全部を K-means に入れればよい、というわけではない。

- K-means は、顧客どうしの**距離**で分ける。似た情報を持つ列を 3 つ入れると、その観点が 3 倍の重みで効く。
- ほとんどの顧客が同じ値の列は、ほぼ全員を同じ側に置くだけで、分ける手がかりにならない (ただし、少数派が距離で強調されて効きすぎることがある。第 2 章)。
- NULL が多い列は、使える顧客が減る。

そこで、**定義を決めること**と**採用すること**を分ける ([ADR 007](../decisions/007_customer_feature_principles.md) の「進め方」)。

```
1. 候補を洗い出し、定義を決める     → customer_features.md、dbt で実装
2. データを見て、採用するかを決める  → notebook 02、ADR 008
```

先に定義を決めて列として作っておけば、採用しなかった列も、あとでクラスタの解釈に使える。実際、不採用の列も `customer_features` に残している。

## 候補の 4 つの区分

[ADR 007](../decisions/007_customer_feature_principles.md) で、候補をあらかじめ 4 つに分けている。

| 区分 | 内容 | 例 |
|---|---|---|
| ① 基本 | どの顧客分析でもまず使うもの | 購入回数、購入金額、最終購入からの日数 |
| ② 行動の違い | 購買行動の中身 | 支払い方法、レビュー |
| ③ 慎重に検討 | NULL が多い / 似た情報 / 顧客より注文の条件の影響が強い | 送料の割合、配送日数 |
| ④ 解釈用 | 入力には使わず、クラスタを説明するのに使う | 州、代表のカテゴリ |

①は RFM (Recency・Frequency・Monetary。最近性・頻度・金額) と呼ばれる、顧客分析の基本の 3 つにあたる。
④を入力にしないのは、K-means がカテゴリの値 (州の名前など) をそのまま扱えないため。

## 判断の観点

notebook 02 の冒頭に、何を見て判断するかを先に書いている。

1. NULL の割合
2. 分布 (ほとんど同じ値か、偏り、外れ値)
3. 特徴量どうしの関係 (似た情報を持つ組)
4. 比較候補の決着
5. 意味 (顧客の行動か、注文の条件か)

**見る前に、何を見て判断するかを書いておく**のは、結果を見てから都合のよい理由を探すのを防ぐため。

### 1・2. NULL と分布: プロファイルの表

```python
profile = pd.DataFrame({
    "null_rate": X.isna().mean(),                     # NULL の割合
    "n_unique": X.nunique(),                          # 値の種類の数
    "top_value_share": X.apply(lambda s: s.value_counts(normalize=True).iloc[0]),  # 最も多い値の割合
    "skew": X.skew(),                                 # 歪度
    "median": X.median(),
    "p99": X.quantile(0.99),
    "max": X.max(),
})
```

- `X.isna().mean()`: `isna()` は NULL なら True。True を 1 として平均すると、NULL の割合になる。
- `value_counts(normalize=True)`: 値ごとの割合を、多い順に並べる。`.iloc[0]` で最も多い値の割合を取る。
- `skew()`: 歪度。0 なら左右対称、大きな正の値なら右に長く裾を引く (少数の大きな値がある)。

この表から分かったこと:

| 見つかったこと | 特徴量 |
|---|---|
| NULL が多い | `avg_card_installments` (22.9%) だけ。ほかは 1.3% 以下 |
| ほとんど同じ値 | `distinct_category_count` (97.7% が 1)、`order_count` (97.0% が 1)、`has_used_voucher` (96.2% が FALSE)、`late_delivery_ratio` (93.0% が 0) |
| 偏りが大きい | 金額 (歪度 8〜10。中央値 約 90 に対して最大 13,440) |

**顧客の約 97% が 1 回しか買っていない**、というデータの構造が、ここで初めてはっきり見える。このあとの判断のほとんどは、この事実に左右される。

### 3. 似た情報を持つ組: 順位相関

```python
corr = X.corr(method="spearman")
```

ふつうの相関 (ピアソン) ではなく、**順位相関 (スピアマン)** を使っている。値そのものではなく、大きさの順位どうしの相関を見る方法。

| | ピアソン | スピアマン |
|---|---|---|
| 見るもの | 直線の関係 | 「一方が大きいほど、もう一方も大きいか」 |
| 外れ値 | 1 人の極端な値に強く引っぱられる | 順位にするため、影響を受けにくい |

金額のように偏りが大きく外れ値がある列には、スピアマンが向いている。

逆に、ピアソンを選ぶのは次のような場合。偏りが小さく外れ値も少ないデータでは、どちらを使ってもほぼ同じ値になるため、「きれいなデータだから」より、次の理由で選ぶことが多い。

| ピアソンを選ぶ状況 | 理由 |
|---|---|
| このあと使う手法が、値の直線関係を前提にしている (線形回帰、PCA など) | 手法と同じものさしで確かめる方が筋が通る |
| 「どれだけ比例しているか」を知りたい | スピアマンは単調かどうかしか見ず、直線か曲線かを区別しない |
| 外れ値が本物で、重要な値 | 順位にすると、大きさの情報が消える |
| データが正規分布に近く、人数が少ない | ピアソンの方が推定が安定する |

補足:

- K-means が実際に見るのは、対数変換・標準化したあとの値 (第 2 章)。厳密には、変換後の値でのピアソン相関が「K-means から見た似ている度合い」になる。log1p で偏りはかなり取れるため、スピアマンと大きくは変わらない。今回の目的 (似た特徴量を見つけて 1 つに絞る) には、スピアマンで十分だった。
- 97% が同じ値の列のように、同じ値 (同順位) が多い列では、どちらの相関も小さく出やすい。0 / 1 の列どうしは、クロス集計で見る方が確実。

絶対値 0.7 以上の組:

| 組 | 順位相関 | 理由 |
|---|---:|---|
| `total_items_amount` と `avg_order_items_amount` | 0.99 | 1 回購入の顧客では同じ値になる |
| `days_since_last_purchase` と `days_since_first_purchase` | 0.99 | 同上 |
| `avg_item_price` と金額 | 0.94〜0.95 | 1 商品だけ買う顧客が多い |
| `freight_ratio` と金額 | −0.78〜−0.82 | 送料は価格に比例しない。安い商品ほど送料の割合が高い |

相関が高い理由を、**データの構造から説明している**ことに注目する。数字だけで捨てるのではなく、「なぜ同じ情報になるのか」を確かめてから、1 つに絞る。

### 4. 比較候補の決着

配送の体験を表す候補が 2 つあった。どちらも、同じ配送の実績を違う方法で要約したもの。

| | `avg_delivery_delay_days` (遅れの日数の平均) | `late_delivery_ratio` (遅れた注文の割合) |
|---|---:|---:|
| 最も多い値の割合 | 7.2% | 93.0% |
| レビューとの順位相関 | −0.18 | −0.31 |

`late_delivery_ratio` を採用した。理由は次のとおり。

- 遅れの日数の中央値は −12 日 (予定より 12 日早く届く)。この値は、顧客の体験より「配送予定日がどれだけ余裕をもって設定されているか」を表している可能性がある。
- 「遅れを経験したか」の方が、顧客の体験として解釈しやすい。遅れの有無でレビューの平均は大きく違う (すべて遅れ 2.26 / 一部遅れ 3.23 / 遅れなし 4.29)。

[ADR 008](../decisions/008_feature_selection.md) には「レビューとの相関が強いことだけを理由にはしていない」と書いてある。相関が強い方を選ぶ、という単純な基準にしない理由は、**何と相関が強ければよいのか**が、目的によって変わるため。

### 5. 欠損の意味を確かめる

レビューがない顧客 (604 人) が、ほかの顧客とどう違うかを見ている。

| | コメントあり | 評価のみ | レビューなし |
|---|---:|---:|---:|
| 遅れを経験した割合 | 9.5% | 4.6% | **23.8%** |
| 配送日数の平均 | 13.3 日 | 11.8 日 | **18.7 日** |

レビューがない顧客は、遅れを経験した割合が高い。つまり、**欠損がランダムに起きていない**。

この場合、NULL を平均値で埋めると、「遅れを経験しやすい顧客」を「平均的な顧客」として扱うことになり、実態を歪める。そのため、単純な補完はしないと決めた (具体的な扱いは第 2 章)。

一方、最終購入からの日数で区切っても、レビューがない割合は変わらなかった (0.1〜0.7%)。「データの終わり近くに買ったので、まだレビューを書いていない」という理由ではないことも、あわせて確かめている。

### この関係をどう見つけたか

すべての列を並べて探したのではない。**欠損を扱う前の決まった確認**と、**理由の仮説**から、比べる列を選んでいる。

```
欠損あり
 → 0. 量と形を見る       何人か、どの列が同時に欠損するか、いつの行か
 → 1. 理由の仮説を立てる  なぜ欠損するのか
 → 2. 仮説ごとに確かめる  支持する結果も、否定する結果も見る
 → 3. 全体を眺める        取りこぼしがないか
 → 4. 扱いを決める        除外 / 補完 / フラグ / 区分として残す
```

**0. 量と形**: レビューの 2 つの列は、同じ 604 人で欠損している (ほかの列の NULL とは重ならない。[ADR 009](../decisions/009_clustering_preprocessing.md))。

**1. 仮説**: 欠損を扱う前には、毎回「欠損している人と、していない人は、ほかの点で違うか」を確かめる。違わなければ欠損はランダムとみなせ、違えば欠損そのものが情報を持つ。比べる列は、欠損が生まれる経路から仮説を立てて選ぶ。

| 経路 | 問い | このデータでの仮説 | 確かめる列 |
|---|---|---|---|
| まだ起きていない (時間) | データの終わりが近く、まだ記録されていないだけでは | 最近買ったので、まだ書いていない | `days_since_last_purchase`、直近 7 日の割合 |
| 記録の仕組み | システムの都合で記録されない場合は | (レビューでは考えにくい) | — |
| 人の行動 | 入力しなかった理由は (不満、満足、面倒) | 体験が悪かった | `late_delivery_ratio`、`avg_delivery_days` |
| 対象の違い | 特定のグループに偏っていないか | 買った金額や商品が違う | `total_items_amount` |

「体験が悪かった」という仮説がすぐ浮かんだのは、直前の比較候補の確認 (4.) で、**遅延とレビューのスコアが強く関係する**と分かっていたから。スコアを下げる要因なら、書くかどうかにも影響するかもしれない、という連想。

**2. 確かめる**: 遅延の仮説は支持され (23.8% と 4.6〜9.5%)、時間の仮説は否定された (日数で細かく区切っても欠損率は変わらない)。仮説を支持する結果を探すだけでなく、**否定する確認も入れている**。
また、レビューなし / 評価のみ / コメントあり の 3 つに分けて比べたため、コメントありの顧客も遅延が多い (9.5%) ことが副産物として見えた。

**3. 全体を眺める**: 仮説を確かめたあと、残りの列もグループごとに並べると、取りこぼしの確認になる。ただし、最初からすべてを並べると、たくさん比べた中で偶然大きく見える差を拾いやすい。欠損が 604 人と少ない今回は、特にその危険が大きい。**仮説から絞った列を先に、全体はあとで**、の順にする。

```python
g = features["avg_review_score"].isna().map({True: "missing", False: "present"})
features.groupby(g)[["late_delivery_ratio", "avg_delivery_days", "days_since_last_purchase", "total_items_amount"]].agg(["mean", "median"])
g.value_counts()  # 人数も必ず出す
```

**4. 扱いを決める**: 欠損がランダムでないため、単純な補完はしない、とした (具体的な扱いは第 2 章)。

## 結果

| 区分 | 特徴量 |
|---|---|
| 採用 (8 つ) | `total_items_amount`、`order_count`、`days_since_last_purchase`、`item_count`、`credit_card_order_ratio`、`avg_review_score`、`has_review_comment`、`late_delivery_ratio` |
| 保留 | `avg_card_installments` (NULL が 22.9%) |

金額・時期・商品・支払い・体験の 5 つの観点から、それぞれ 1〜3 個が残るようにしている。

## 次の段階への申し送り

[ADR 008](../decisions/008_feature_selection.md) の「次の段階で確認すること」は、このあと実際に起きた問題をほぼ予告している。

- 97% が 1 回購入のため、K-means が購買行動ではなく、ほかの違いで顧客を分ける可能性がある
- 0 / 1 に近い特徴量を標準化すると、少数派の値ほど大きな値になる (93% が 0 の `late_delivery_ratio` は、1 が約 +3.6 になる)
- シルエット係数が高いことだけで、良い結果と判断しない

**選んだ時点で、気になる点を書き残しておく**と、次の段階で何を確かめればよいかがはっきりする。

## まとめ

```
定義を決めること と 採用すること を分ける (不採用の列も解釈に使う)
見る前に、判断の観点を書く
  1. NULL の割合
  2. 分布        … ほとんど同じ値か、偏り (歪度)
  3. 似た情報    … 順位相関 (偏りや外れ値に強い)。相関が高い理由をデータの構造で説明する
                   ピアソンは、後の手法が直線関係を前提にするときや、比例の度合いを知りたいときに選ぶ
  4. 比較候補    … 何と相関が強ければよいかは、目的で決まる
  5. 意味        … 顧客の行動か、注文の条件か
欠損がランダムでないかを確かめる (レビューなし = 遅延が多い) → 単純に補完しない
  量と形 → 理由の仮説 (時間 / 記録の仕組み / 人の行動 / 対象の違い) → 確かめる (否定も) → 全体を眺める → 扱いを決める
気になる点は、次の段階への申し送りとして書き残す
```

## 確認の問い

- `avg_order_items_amount` を不採用にしたのはなぜか。このデータで、`total_items_amount` とほぼ同じになる理由は何か。
- 相関を見るのに、ピアソンではなくスピアマンを使ったのはなぜか。
- レビューがない顧客の NULL を、平均値で埋めなかったのはなぜか。
- 欠損の理由の仮説を、4 つの経路 (時間・記録の仕組み・人の行動・対象の違い) に沿って挙げられるか。
