# 006. mart の設計方針

- 日付: 2026-10-19
- ステータス: 決定

## 背景

[002](002_layer_architecture.md) で、判断が入る処理 (行の除外、重複の排除、集約など) はすべて mart で行うと決めた。
また、mart には粒度の異なる 2 つのテーブル (注文単位と顧客単位) を作ると決めた。

staging の作成までに、「mart で決める」として先送りしてきた論点がいくつかある
([data_notes.md](../data_notes.md)、[notebooks/01_order_reviews_duplicates.ipynb](../../notebooks/01_order_reviews_duplicates.ipynb))。
顧客セグメンテーションのための mart を作る前に、それらの方針を決める。

| # | 論点 |
|---|---|
| A | 分析の対象にする注文 (購入成立の定義) |
| B | 注文の金額の定義 |
| C | レビューの扱い |
| D | 最終購入からの日数の基準日 |
| E | 既知の不整合の扱い |
| F | テーブル名と列名 |

以下の件数は、すべて 2026-10-19 時点の staging のデータで集計したもの。

## 決定

### A. 分析の対象にする注文

**`order_status = 'delivered'` の注文だけを「購入が成立した注文」とし、分析の対象にする。**

#### 理由

- **delivered 以外の注文は、完了しなかった注文である。**
  shipped、invoiced、processing なども、処理の途中ではなく、配送予定日を過ぎたまま止まっている
  (例: shipped の 1,107 件は、全件が配送予定日を過ぎており、配達日時が 1 件もない)。
  どのステータスもデータの全期間に散らばっており、データの切り出し時点で処理中だった注文ではない。

  | ステータス | 注文数 | 配送予定日を過ぎた注文 | 配達日時がある注文 |
  |---|---:|---:|---:|
  | delivered | 96,478 | 96,475 | 96,470 |
  | shipped | 1,107 | 1,107 | 0 |
  | canceled | 625 | 620 | 6 |
  | unavailable | 609 | 609 | 0 |
  | invoiced | 314 | 314 | 0 |
  | processing | 301 | 301 | 0 |
  | created | 5 | 5 | 0 |
  | approved | 2 | 2 | 0 |

- **支払いのレコードの有無では判断できない。** キャンセルされた注文や unavailable の注文にも、0 円より多い支払いのレコードが残っている。
- **特徴量を同じ注文の集まりから計算できる。** 配送やレビューに関する特徴量は、配達された注文でなければ意味がない。対象を delivered にそろえることで、金額・配送・レビューの特徴量をすべて同じ注文から計算できる。
- **対象から外れる顧客は少ない。**

  | 対象にする注文 | 残る顧客 | 外れる顧客 |
  |---|---:|---:|
  | すべて | 96,096 | 0 |
  | canceled と unavailable だけを除く | 94,990 | 1,106 (1.2%) |
  | delivered だけ | 93,358 | 2,738 (2.8%) |

#### この判断で失うもの

- delivered の注文が 1 件もない 2,738 人は、セグメンテーションの対象から外れる。購入が成立しなかった顧客の分析は、今回の目的 (購買行動による顧客のグループ分け) の範囲外とする。
- delivered とそれ以外の注文の両方を持つ顧客 (199 人) は、delivered の注文だけで特徴量を計算する。

### B. 注文の金額の定義

**金額は明細 (`order_items`) から計算する。購入金額は価格だけとし、送料は別の列として持つ。**

| 列 | 定義 |
|---|---|
| `items_amount` | 明細の価格 (`price`) の合計。**購入金額**として使う |
| `freight_amount` | 明細の送料 (`freight_value`) の合計 |
| `total_amount` | `items_amount` と `freight_amount` の合計 (明細ベースの商品価格 + 送料)。支払いの合計とは一致しない注文がある |

支払い (`order_payments`) のデータは金額の計算には使わず、支払い方法や分割回数など、支払いの行動に関する特徴量に使う。

#### 理由

- **明細と支払いの金額は、ほぼ一致する。** delivered の 96,478 注文のうち、96,178 注文 (99.7%) で、明細の「価格 + 送料」と支払いの合計が 1 セント以内で一致する。ずれの合計は、全体の約 1,540 万レアルに対して 0.02% である。

  | 明細との関係 | 注文数 | 差額の合計 | 備考 |
  |---|---:|---:|---|
  | 一致 | 96,178 | 0 | |
  | 支払いのほうが多い | 260 | +3,031 レアル | 245 件が分割払い。分割の手数料と考えられる |
  | 支払いのほうが少ない | 39 | −199 レアル | 原因は不明 |
  | 支払いのレコードがない | 1 | - | |

- **明細のほうが、商品への支出を表す。** 支払いとのずれの多くは分割の手数料と考えられ、商品にいくら使ったかとは別のものである。
- **明細は商品ごとの金額のため、カテゴリごとの金額などの特徴量も、同じデータから一貫して計算できる。**
- **支払いのレコードがない注文でも、金額を計算できる。**
- **購入金額に送料を含めない理由:**
  送料は、商品の価格とは別の要因 (配送先の地域、商品の大きさ・重さ、配送条件など) で決まると考えられる。
  購入金額に送料を含めると、顧客が商品にどれだけお金を使ったか以外の要因が混ざるため、購入金額は価格だけにし、送料は別の列として持つ。
  送料は金額全体の 14% (1 注文あたりの中央値は 18%) を占める。
  地域ごとに送料の平均に差は見られたが (サンパウロ州 17.3 レアル、北部 6 州 41.2 レアル)、商品の違いも含んだ比較であり (価格の平均も、それぞれ 125.1 レアル、183.1 レアルと異なる)、地域との関係は必要になった時点で検証する。

### C. レビューの扱い

A に従い、delivered の注文に付いたレビューだけを使う。

| 状態 (delivered の注文) | 注文数 |
|---|---:|
| レビューが 1 件 | 95,307 |
| レビューが複数 | 525 |
| レビューがない | 646 |

#### 処理の手順

次の順序で処理する。

| 順序 | 処理 | テーブル | 対象 |
|:---:|---|---|---|
| 1 | 時系列が矛盾しているレビュー (作成日が購入日より前) を除く | 注文単位 | 6 件 |
| 2 | 残ったレビューから、注文ごとに 1 件を採用する | 注文単位 | 複数あるのは 525 注文 |
| 3 | 採用したレビューの `review_id` とスコアを、注文単位のテーブルに持たせる | 注文単位 | |
| 4 | `review_id` の重複を除いてから、スコアを平均する | 顧客単位 | |

1 を 2 より先に行うのは、時系列が矛盾しているレビューが「最新の回答」として採用されるのを防ぐためである。

#### 1 注文に 1 件を採用するルール (手順 2)

**回答日時 (`review_answered_at`) の降順、次に `review_id` の昇順で並べ、先頭の 1 件を採用する。**
回答日時が NULL のレビューは最後に回し、すべて NULL の場合は `review_id` の昇順で決まる。

```sql
order by review_answered_at desc nulls last, review_id asc
```

- 最新の回答は、その注文に対する最終的な評価を反映すると考え、採用する。
- 並び順を最後まで指定することで、何度実行しても同じレビューが選ばれる。
- 回答日時が NULL のレビューは、現在のデータにはない。staging の非欠損テスト (エラー) があるため、入ってきた場合は mart を作る前に検知できる。
- 他の案として、スコアの平均も考えられる。レビューは回答という単位のデータであるため、1 件を選ぶ方法を採用した。対象は delivered の注文の 0.5% であり、どちらを選んでも結果への影響は小さい。

#### 顧客単位での重複の除き方 (手順 4)

**顧客単位でスコアを平均する直前に `review_id` の重複を除き、同じ回答を 1 回だけ数える。**

- 1 つのレビューが複数の注文に付いていることがあり (delivered で 1,309 注文)、注文ごとに数えると同じ回答を二重に数えてしまう。
  影響は 18 人 (最大 0.75 点の差) と小さいが、二重計上を防ぐという mart の設計の考え方に合わせる。
- 前提: 同じ `review_id` は、顧客・スコア・内容 (作成日、回答日時、コメント) がすべて同じであること。
  複数の注文に付いた 789 件のレビューすべてで成り立っている。**この前提を dbt のテストとして書き**、崩れた場合に検知できるようにする。

#### レビューがない場合

- **スコアは NULL にし、0 などの値で埋めない。** 「低い評価」と「評価がない」を区別するためである。
- 件数は、注文単位で 646 件、顧客単位で 603 人。
- 時系列が矛盾して除いたレビューの注文も、「レビューなし」として扱う。注文は残す (A・E と一貫)。
- セグメンテーションの段階で NULL を扱えない手法を使う場合は、値の補完や「レビューの有無」のフラグの追加を検討する。

### D. 最終購入からの日数の基準日

**基準日は、A で対象にした注文 (delivered) の最後の購入日 (2018-08-29) とする。**

- 日付を SQL に直接書かず、対象の注文から計算する (`max(date(order_purchased_at))`)。A で決めた対象の注文と、基準日が必ずそろうようにするためである。
- 日数は、日付どうしで計算する (購入日時ではなく購入日を使う)。同じ日に購入した顧客に、時刻による差がつかないようにするためである。
- 顧客単位のテーブルに、基準日そのものも列 (`reference_date`) として持たせ、日数がどの日を基準にした値かを確認できるようにする。

#### 理由

基準日は、「最終購入からの日数」などの時間に関する特徴量を計算するために必要になる。

| 案 | 基準日 | 評価 |
|---|---|---|
| 実行した日 | 実行するたびに変わる | 結果が再現できない。データは 2018 年で終わっているため、全員が約 3,000 日前になり、値を読めない |
| 全注文の最後の購入日 | 2018-10-17 | 対象外のキャンセルされた注文で決まる。全員に 49 日の空白が上乗せされる |
| **対象の注文の最後の購入日** | **2018-08-29** | 分析の対象と同じ注文から決まる。「0 日 = データの最終日に購入した」と読める |

基準日を固定する効果は、次のところに現れる。

- **再現性**: 何度実行しても同じ値になる。
- **値の読みやすさ**: 日数をそのまま解釈できる。
- **比やしきい値の正しさ**: 日数の比を使う場合や対数を取る場合、「90 日以内ならアクティブ」のようなしきい値を使う場合に、基準日によって結果が変わる。
  (日数の差は基準日によらないため、標準化してから k-means などにかけるだけなら、結果への影響は小さい。)
- **特徴量の時点の一貫性**: 時間に関するすべての特徴量を、同じ 1 日の時点で見た顧客の状態としてそろえる。

#### 注意点

- **データの最後の 1 週間ほどは不完全である。** delivered の注文は、2018-08-20 には 1 日あたり約 250 件あったが、8 月 24 日に 96 件、8 月 29 日に 11 件と急に減り、8 月 30 日以降はない。
  データの切り出し時点で配送中だった注文が含まれていないと考えられる。そのため、最終購入から数日以内の顧客は、実際より少なく見えている可能性がある。
- 分析の期間を 8 月前半までで区切る方法もあるが、実際に配達された注文を捨てることになるため、採用しない。

### E. 既知の不整合の扱い

#### 基本方針

- **注文や明細は除外しない。** 不整合な値は、それを使う特徴量の計算でだけ NULL として扱い、推測で値を埋めない。
- **不整合な値は修正しない。** data_notes への記録と、警告テストによる検知を続ける。
- 「現在の特徴量では使用しない」ことは、「データ品質の問題がない」ことを意味しない。使用しない列の不整合も、記録と検知の対象とする。

注文ごと除外しないのは、1 つの値の問題で、正しく計算できるほかの特徴量まで失わないためである。
値を推測で埋めないのは、C でレビューがないことを NULL で表したのと同じく、わからないことを区別して残すためである。

#### 特徴量に影響する不整合 (delivered の注文)

| 不整合 | 件数 | 影響する特徴量 | 扱い |
|---|---:|---|---|
| 配達日時がない | 8 注文 | 配送日数、配送の遅れ | その特徴量だけ NULL にする。注文は残す |
| 支払いのレコードがない | 1 注文 | 支払い方法、分割回数 | その特徴量だけ NULL にする。金額は明細から計算するため影響しない |
| 分割回数が 0 | 2 注文 | 分割回数 | その値を NULL として扱う |
| カテゴリがない | 1,392 注文 (1,537 明細) | カテゴリに関する特徴量 | カテゴリは NULL のまま。明細は金額の計算に含める |
| カテゴリの英訳がない | 2 カテゴリ (22 明細) | カテゴリに関する特徴量 | ポルトガル語名で代用する。同じカテゴリの別の表記であり、推測による補完ではない |
| レビュー作成日が購入日より前 | 6 件 | レビューのスコア | C のとおり、そのレビューは使わない |

#### 現時点では特徴量に使用しない列の不整合

値は修正せず、記録と警告テストによる検知を続ける。

| 不整合 | delivered | 全注文 | 検知 |
|---|---:|---:|---|
| 承認日時がない | 14 | - | 既存 (delivered を条件とした非欠損テスト) |
| 発送日時がない | 2 | - | 既存 (同上) |
| 購入日時 > 承認日時 | 0 | 0 | 追加 (順序の逆転のテスト) |
| 承認日時 > 発送日時 | 1,350 | 1,359 | 追加 (同上) |
| 発送日時 > 配達日時 | 23 | 23 | 追加 (同上) |
| 発送期限が 2020 年 | 1 | 3 | 列の説明に記録済み |

- **欠損の検知と、順序の逆転の検知は分ける。** 欠損している日時とは順序を比べられないため、順序のテストは 2 つの日時がどちらも存在する行だけを対象にする。
- 順序の逆転は、時間差が 1 時間未満から数日以上までばらばらで、一定のずれではない。タイムゾーンの違いではなく、記録のタイミングや入力の問題と考えられる (原因は特定できていない)。
- 配送の特徴量 (購入から配達までの日数、配送予定日と実際の配達日の差) は、承認日時と発送日時を使わないため、順序の逆転の影響を受けない。配達日時が購入日時より前の注文はない。

### F. テーブル名と列名

#### テーブル

| テーブル | 粒度 | 内容 |
|---|---|---|
| `fct_delivered_orders` | 1 行 = 1 注文 (delivered のみ) | 注文の金額・支払い・配送・レビューをまとめる |
| `customer_features` | 1 行 = 1 人 (`customer_unique_id`) | `fct_delivered_orders` を集約した特徴量。セグメンテーションの入力 |

- **注文単位のテーブルには、delivered の注文だけを入れる。** 全注文を入れて顧客単位で絞り込む案もあるが、集計のたびに絞り込む必要があり、忘れると誤った特徴量になる。今回は、使い回しやすさよりも間違えにくさを優先する。ほかの分析が必要になった場合は、そのときにテーブルを追加する。
- **`fct_delivered_orders`**: 注文という出来事を 1 行ずつ記録し、金額などの数値を持つため、dbt で一般的な `fct_` (fact) を付ける。名前に `delivered` を入れ、中身が delivered の注文だけであることを名前からわかるようにする。
- **`customer_features`**: ほかのテーブルと結合するための顧客の属性 (`dim_`) ではなく、セグメンテーションに入力する特徴量の表であるため、役割をそのまま名前にする。
- 層 (mart であること) はデータセット名 `olist_mart` で表されるため、テーブル名に `mart_` は付けない。

#### 列名

| 種類 | ルール | 例 |
|---|---|---|
| 日時 | `_at` で終わる (staging と同じ) | `order_purchased_at` |
| 日付 | `_date` で終わる (staging と同じ) | `reference_date` |
| 金額 | `_amount` で終わる | `items_amount`, `freight_amount` |
| 件数 | `_count` で終わる | `order_count`, `item_count` |
| 日数 | `_days` で終わる | `days_since_last_purchase`, `delivery_days` |
| 真偽 | `is_`、`has_` で始まる | `has_review` |

## 影響

- `fct_delivered_orders` は、明細・支払い・レビューをそれぞれ注文単位に集計してから結合し、二重計上を防ぐ。
- mart の検証として、粒度と一意性、NULL のテストに加え、金額の突き合わせ (`fct_delivered_orders` の金額の合計が、staging の delivered の注文の明細の合計と一致するか) をテストする。
- staging の `stg_orders` に、日時の順序の逆転を検知する警告テストを 3 つ追加する。
- data_notes に、日時の順序の逆転と、データの最後の 1 週間が不完全であることを追記する。
- 顧客単位の特徴量の具体的な定義 (どの特徴量を作るか) は、この ADR の方針に従って別に決める。

## 見直す条件

- 購入が成立しなかった顧客 (キャンセルのみの顧客など) も分析の対象にしたくなった → A と F (注文単位のテーブルの中身) を見直す
- 支払いの手数料を含めた、実際の支払額で分析したくなった → B を見直す
- 同じ `review_id` で顧客やスコアが異なるデータが現れた (テストで検知) → C の手順 4 を見直す
- データが更新され、最後の期間が不完全でなくなった、または期間が延びた → D の注意点を見直す
