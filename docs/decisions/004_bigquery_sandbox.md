# 004. BigQuery サンドボックスで運用する

- 日付: 2026-10-08
- ステータス: 決定

## 背景

BigQuery を使うための GCP プロジェクトを作成した (名前: `olist-data-platform`、ID: `olist-data-platform-511008`)。
このプロジェクトは費用をかけずに進めることを前提としている。

以前作成した請求先アカウントは無料トライアル用のもので、トライアルはすでに終了している。
そのため、課金を有効にするには、有料アカウントへのアップグレードが必要になる。

## 決定

アップグレードはせず、請求先アカウントを紐付けない **BigQuery サンドボックス** で運用する。

## 理由

- **課金が発生しないことを、仕組みとして保証できる。**
  請求先アカウントがなければ、操作を誤っても請求は起きない。
  有料アカウントでは、予算アラートやクエリ上限の設定に頼ることになり、設定の誤りや漏れで請求が起きる可能性が残る。
- **サンドボックスの制約は、このプロジェクトでは問題にならない。**
  - データ量は約 120MB で、無料の範囲 (保存 10GB、クエリ 1TB / 月) に十分収まる。
  - 使う予定の機能 (ローカルの CSV の読み込み、ビュー・テーブルの作成、dbt のテスト) は制約の対象外。

## 検討した代替案

### 有料アカウントにアップグレードする

Always Free の範囲は引き続き無料で、テーブルが自動で消えることもない。
ただし、無料の範囲を超えた分は請求されるため、予算アラートとクエリ上限の設定が必須になる。
費用をかけない前提に対して、リスクを残す理由がないため採用しない。

## 影響

- **テーブルは作成から 60 日で自動的に削除される。**
  そのため、BigQuery 上のデータはすべてコードから作り直せるようにする。
  - raw: 読み込みスクリプトで CSV から作り直す
  - staging / mart: `dbt run` で作り直す
  - BigQuery のコンソールで手作業で作ったテーブルに依存しない
- 予算アラートやクエリ上限の設定は不要。

## 見直す条件

- サンドボックスでは使えない機能が必要になった
  (例: セグメンテーションに BigQuery ML を使う場合、サンドボックスで使えるかをその時点で確認する)
- 60 日ごとの作り直しが負担になった
