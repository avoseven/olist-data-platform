# 007. 顧客単位の特徴量の設計原則

- 日付: 2026-10-21
- ステータス: 決定

## 背景

[006](006_mart_design.md) で決めた方針に従い、顧客セグメンテーションに使う顧客単位の特徴量 (`customer_features`) を設計する。

顧客単位の特徴量は、注文・明細・支払い・レビューといった粒度の異なるデータを集約して作る。
集約の仕方 (どの単位で数えるか、平均をどう取るか、NULL をどう扱うか) によって、同じ名前の特徴量でも意味が変わり、二重計上も起きやすい。
特徴量ごとにばらばらに決めると、特徴量どうしの考え方が一貫しなくなるため、共通の原則を先に決める。

また、2 回以上購入した顧客は約 3% しかいない。K-means を使う予定であり、似た特徴量を多く入れると、特定の観点がクラスタリングの結果に強く効きすぎるおそれがある。
特徴量を増やすこと自体を目的にせず、候補を整理してから採用を判断する進め方も、あわせて決める。

## 決定

### 原則 1: 顧客単位の集計の基準は注文ファクトとし、明細などの詳細が必要な特徴量は、粒度を管理した別の集計を使う

- 顧客単位の集計は、`fct_delivered_orders` (1 行 = 1 注文) を基準にする。
- 明細・支払い・レビューは、`fct_delivered_orders` を作る段階で、それぞれ注文単位に集約しておく。これにより、明細と支払いを結合して行が増える二重計上を防ぐ。
- カテゴリ別の情報が必要な特徴量は、注文ごとにカテゴリを 1 つ持たせるだけでは正しく計算できない (1 つの注文に複数のカテゴリの商品が含まれることがあるため)。
  こうした特徴量は、明細から粒度を明示した別の集計 (例: 1 行 = 顧客 × カテゴリ) を作り、そこから計算する。
  別の集計を使う場合も、対象の注文は `fct_delivered_orders` と同じ (delivered の注文だけ) にそろえる。

### 原則 2: 平均や割合は、どの単位を基準にするかと、計算の仕方を明示する

特徴量ごとに、注文単位・明細単位・レコード単位のどれを基準にするかと、次のどの計算の仕方を使うかを、理由とあわせて決める。

| 計算の仕方 | 例 | 意味 |
|---|---|---|
| 注文ごとの値の平均 | 注文ごとの分割回数を出してから、注文間で平均する | 1 回の購入でどういう行動をとるか (どの注文も同じ重み) |
| レコードの平均 | 支払いレコードの分割回数を、そのまま平均する | レコードの多い注文ほど、結果への影響が大きくなる |
| 合計どうしの比 | 送料の合計 ÷ 金額の合計 | 全体としてどれくらいの割合か (金額の大きい注文ほど重みが大きい) |

原則 1 で支払いなどを注文単位に集約するため、「レコードの平均」を使う場面は基本的にない。
ただし、「注文ごとの値の平均」とは意味が異なることを明確にするため、区別して記載する。

### 原則 3: NULL は除いて計算し、すべて NULL なら結果も NULL にする

- 平均などは、NULL の値を除いて計算する。
- 対象の値がすべて NULL の顧客は、結果を NULL にし、0 では埋めない。
- 0 は、観測した結果が 0 だった場合だけに使う。
  例: カテゴリの種類の数は、カテゴリがわかる商品がなければ 0 ではなく NULL にする。「カテゴリがわかる商品がない」ことと「カテゴリの数が 0」であることは区別する。
- 真偽値の特徴量は、NULL を除くだけでは意味が決まらない場合がある (例: レビューそのものがない顧客を FALSE にするか NULL にするか)。特徴量ごとに、定義で明示的に決める。

### 原則 4: 代表値は、同数のときの決め方まで決める

- 複数の値から 1 つを選ぶ特徴量 (代表の支払い方法、代表のカテゴリ、州など) は、同数のときの決め方まで指定し、何度実行しても同じ結果になるようにする。
- 同数のときは、辞書順などの固定のルールで決める。「最後の注文」のように順序で選ぶ場合は、並び順を最後まで指定する。

### 特徴量の区分と進め方

候補は、いきなりすべてを採用する前提にせず、次の 4 つに分けて扱う。

| 区分 | 内容 |
|---|---|
| ① 基本 | 購入回数、購入金額、最終購入からの日数など |
| ② 行動の違い | 支払い方法やレビューなど、購買行動の中身の違いを捉えるもの |
| ③ 慎重に検討 | NULL が多いもの、互いに似た情報を表すもの、顧客の行動より注文の条件の影響が強いもの |
| ④ 解釈用 | クラスタリングには入力せず、できたクラスタを説明するために使う属性 (州、代表のカテゴリなど) |

進め方は次のとおりとする。

1. 候補を洗い出し、計算の定義を決める。
2. 定義に従ってデータを確認し (分布、NULL の割合、特徴量どうしの関係)、クラスタリングに採用するものを決める。

定義を決めることと、クラスタリングに採用することは分けて判断する。定義を先に決めておけば、データを確認した結果採用しないと判断しても、設計をやり直す必要がない。

## 影響

- 特徴量ごとの定義は [customer_features.md](../customer_features.md) にまとめる。定義の細かな修正は仕様書で行い、この ADR の原則を変える場合は新しい ADR を書く。
- `customer_features` を実装する際は、`fct_delivered_orders` と、顧客 × カテゴリの集計の 2 つを入力にする。

## 見直す条件

- リピーターが大きく増えるなど、データの性質が変わり、注文ごとの値の平均では顧客の行動を表しにくくなった
- K-means 以外の手法 (NULL やカテゴリ値をそのまま扱える手法など) を使うことになり、区分④の属性を入力に使えるようになった
