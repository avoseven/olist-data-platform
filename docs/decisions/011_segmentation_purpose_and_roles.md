# 011. セグメンテーションの目的と、指標の役割の分担

- 日付: 2026-10-29
- ステータス: 決定

## 背景

[010](010_rule_flags_and_clustering_scope.md) で、リピーターと遅延経験者をフラグで分け、残りの顧客をクラスタリングした ([notebooks/04_clustering_after_flags.ipynb](../../notebooks/04_clustering_after_flags.ipynb))。

- 金額と最近性の 2 次元の分布には、はっきり分かれた塊がなかった。K-means は、自然にまとまった顧客群を見つけたというより、連続した分布を区切ったと考えられる。
- レビューを加えると、レビューの低い顧客が切り出されたが、その境目はほぼレビューの値の閾値 (1〜3 と 4〜5) で決まっていた。

得られたクラスタは、金額・最近性・レビューの「高い / 低い」の組み合わせとして説明でき、K-means でなくても作れる分け方だった。
そのため、最終的なセグメントは説明しやすいルールで作ることにした。

ルールを決める前に、セグメンテーションの目的と、各指標の役割を決める必要がある。

## 決定

### 1. 目的

**顧客の購買傾向と購入体験を理解し、ビジネス上の改善機会を探る。**

| 観点 | 位置づけ | 成果物で行うこと |
|---|---|---|
| 購買傾向を理解する | 主な分析の目的 | 顧客を分類し、購買の特徴や購入体験の違いを明らかにする |
| 販促の対象を選ぶ | 応用・考察 | 分析結果から考えられる施策の候補を示す |
| 施策の効果の検証 | 対象外 | 施策を実施したあとのデータがないため、効果があるかは判断しない |

結果は、次の 3 つを分けて示す。

1. データから確認できた事実
2. そこから考えられる解釈
3. 検証すべき施策の仮説

### 2. 指標の役割

| 役割 | 指標 |
|---|---|
| **セグメンテーション** (購買傾向) | 購入回数 (リピーターかどうか)、購入金額 |
| **セグメントどうしで比べる指標** (購入体験) | 配送の遅れ、配送日数、レビューの評価、レビューの有無、コメントの有無 |
| **比べるときの確認用の指標** | 購入時期 |
| **解釈を補う属性** | カテゴリ、州、支払い方法、複数商品の購入 |

### 3. セグメンテーションの軸

| セグメント | 条件 |
|---|---|
| リピーター | `order_count >= 2` |
| 単発購入 (金額で区切る) | `order_count = 1` の顧客を、`total_items_amount` で区切る |

- 金額の区切り方 (閾値と区分の数) は、候補 (中央値、四分位、切りのよい値、K-means の境界など) の人数と顧客像を比べてから決める。K-means の境界は、自然な境目とは限らないため、候補の 1 つとして扱う。
- リピーターは、まず 1 つのセグメントとして扱う。分けるかは、比べた結果を見てから判断する。

### 4. NULL の扱い

分類に使う指標 (`order_count`・`total_items_amount`) には NULL がないため、**全顧客 (93,358 人) を分類する**。
購入体験の分析では、指標の意味に応じて扱いを変え、補完はしない。

- 平均や割合 (レビューの評価、遅延率など): NULL の顧客は分母に入れず、計算に使った人数をあわせて示す。
- レビューの有無: 「レビューなし」を 1 つの区分として、投稿率や、レビューなしの顧客の遅延率などを比べる。

## 理由

### 遅延経験を分類の条件から外す理由

- 分類の条件に使うと、遅延経験者とそうでない顧客が最初から別のセグメントになる。セグメントどうしの遅延率を比べても、分けた条件を確かめるだけになり、新しい発見につながりにくい。
- 購入体験の指標として残せば、「金額の大きい顧客ほど遅延が多いか」「リピーターと単発購入の顧客で、レビューの評価や投稿率が違うか」などを比べられる。違いが見つかっても因果関係を示したことにはならないが、施策の仮説の材料になる。
- レビューの評価も同じ理由で、分類の条件にしない。レビューは配送の体験の影響を受ける (遅延経験者の 73.5% はレビューの平均が 3 以下。遅延のない単発購入の顧客では 17.4%)。一方、レビューが 3 以下の顧客の 75% は遅延を経験しておらず、遅延だけでは説明できない。レビューは顧客の性質ではなく、購入体験の評価として扱う。

### 購入時期を分類の軸にしない理由

- 単発購入の顧客にとっての購入時期は「いつ購入したか」、リピーターにとっては「最後にいつ購入したか」で、意味が異なる。
- 購入体験は、購入した月によって大きく変わる。delivered の注文の遅延率は、月によって 1.2% (2018-06) 〜 19.0% (2018-03) と差があり、遅延率の高い月はレビューの平均も低い (2018-03 は 3.81)。購入時期で分類すると、セグメントどうしの違いが、顧客の違いではなく購入した時期の違いを反映するおそれがある。
- 最近の月ほど配送日数が短い (2018-08 は 7.7 日)。データの最終日までに配達が終わった注文だけが delivered に入るため、最近の月は配送の早い注文に偏っている可能性がある。
- データは 2018-08-29 で終わっている。最終購入からの日数は計算できるが、それだけで顧客が離脱したとは言えない。

購入時期は、セグメントどうしの違いが同じ時期の注文どうしでも残るかを確かめるために使う。

### 金額で区切るのを単発購入の顧客だけにする理由

- `total_items_amount` は、リピーターにとっては複数回の購入の合計で、単発購入の顧客の 1 回の金額とは意味が異なる。同じ閾値を当てはめると、購入回数の違いが金額の違いとして現れる。

### 指標の役割を分ける理由

- 分類に使う指標と、分類したあとで比べる指標を分けることで、「分類の条件を確かめただけ」の比較を避けられる。
- セグメンテーションを分類だけで終わらせず、セグメントどうしの比較と、施策の仮説までつなげられる。

## 影響

- [010](010_rule_flags_and_clustering_scope.md) のうち、遅延経験をフラグで分けることと、最終的なセグメントにクラスタリングを使うことは、この ADR で置き換える。クラスタリングの結果 ([03](../../notebooks/03_clustering.ipynb)・[04](../../notebooks/04_clustering_after_flags.ipynb)) は、ルールでセグメントを作ると判断した根拠として残す。
- [009](009_clustering_preprocessing.md) の NULL の扱い (学習から外す) は、クラスタリングの試行のためのもので、セグメンテーションには使わない。
- セグメンテーションでは K-means を使わないため、金額の対数変換や標準化も行わない。

## 見直す条件

- 単発購入の顧客の金額の区切り方で、顧客像の違いがほとんど出ない → 区分の数や、使う指標を見直す
- リピーターの中で、購入体験に大きな違いがありそう → リピーターを分けることを検討する
- 購入時期をそろえると、セグメントどうしの違いがなくなる → その違いは時期によるものとして扱い、解釈を見直す
