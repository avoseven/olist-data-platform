# 001. BigQuery に取り込むテーブルの選定

- 日付: 2026-10-08
- ステータス: 決定

## 背景

このプロジェクトの目的 (暫定) は、Olist のデータを使った**顧客セグメンテーション**である。

Olist のデータは 9 テーブルある (詳細は [data_notes.md](../data_notes.md))。
BigQuery に取り込む前に、目的に対してどのテーブルが必要かを決める。

## 決定

以下の 7 テーブルを取り込む。`sellers` と `geolocation` は取り込まない。

| 区分 | テーブル | セグメンテーションでの用途 |
|---|---|---|
| 主要 | `customers` | 顧客の識別 (`customer_unique_id`) と地域 (州・市) |
| 主要 | `orders` | 購入日時 (最終購入日・購入回数)、配送の実績と予定 |
| 主要 | `order_items` | 購入金額、送料、購入した商品 |
| 主要 | `products` | 商品のカテゴリ |
| 分析用 | `order_payments` | 支払い方法、分割払いの回数 |
| 分析用 | `order_reviews` | レビューのスコア (購入体験の満足度) |
| 分析用 | `product_category_name_translation` | カテゴリ名の英訳 (結果を解釈しやすくするため) |

## 理由

### 取り込まないテーブル

- **`sellers`**: 販売者についての情報であり、顧客の特徴にはならない。
- **`geolocation`**: 顧客の地域は `customers` の州・市で表せる。緯度経度が必要になるのは距離を計算する場合くらいである。
  加えて、使うには前処理の手間がかかる。
  - 郵便番号が一意でないため、郵便番号ごとに集約する必要がある
  - `customers` のうち 278 行は郵便番号が `geolocation` に存在せず、結合できない

### 全テーブルを取り込む案と比べて

全 9 テーブルを取り込んでも約 121MB で、BigQuery の無料枠には十分収まる。容量やコストは判断の理由にならない。

それでも絞るのは、取り込んだテーブルについては、使わなくても**スキーマの定義・読み込み・テストを保守し続ける必要がある**ためである。
目的に必要なテーブルに絞ることで、パイプラインと検証の範囲を小さく保つ。

## 影響

- `order_items.seller_id` は、結合先のない列として残る。
- data_notes.md の注意点のうち、`geolocation` に関するもの (郵便番号の重複・結合できない郵便番号) は対応不要になる。

## 見直す条件

次のような特徴量や分析が必要になった場合は、この判断を見直す。

- 顧客と販売者の距離 (配送距離) を特徴量にしたい → `sellers` と `geolocation` を追加する
- 販売者の属性 (所在地など) を特徴量に使いたい → `sellers` を追加する
  (何人の販売者から買ったかは `order_items.seller_id` だけで計算できるため、追加は不要)
- セグメンテーションの対象を、顧客から販売者に広げる → `sellers` を追加する
