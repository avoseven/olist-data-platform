# 010. ルールで分ける顧客特性と、クラスタリングで探す顧客特性を分ける

- 日付: 2026-10-29
- ステータス: 決定

## 背景

[008](008_feature_selection.md) で選んだ 8 つの特徴量と、[009](009_clustering_preprocessing.md) の前処理で、K-means の基準となる結果を作った ([notebooks/03_clustering.ipynb](../../notebooks/03_clustering.ipynb))。

基準結果から、次のことがわかった。

- **0 / 1 に近い特徴量が、クラスタの分割を決めていた。** 複数回購入・配送の遅れ・複数商品・カードの利用・コメントの有無の組み合わせで、クラスタがほぼ説明できた。少数派の値ほど標準化で大きな値になり、距離に強く影響したと考えられる。
- **金額と最終購入からの日数は、分割にほとんど効いていなかった。** クラスタで説明できるばらつきの割合 (R²) は、金額で 0.06 以下、最終購入からの日数は k = 7 まで 0.00。
- **k を増やしても、それまでのクラスタはほとんど変わらず、特定の顧客群が 1 つずつ切り出された。**

シルエット係数が最も高い k = 3 も、少数派の顧客がはっきり分かれた結果であり、購買行動の違いを捉えたとは言えない。
これは K-means の精度の問題ではなく、条件で直接判定できる顧客特性と、データから見つけたい顧客特性が、同じ入力に混ざっていたことによると判断した。

## 決定

顧客特性を、**ルールで分けるもの**と、**クラスタリングで探すもの**に分ける。

### 1. ルールで分ける顧客特性 (フラグ)

業務上の意味がはっきりしていて、条件で直接判定できるものは、フラグとして持つ。

| フラグ | 条件 | 人数 |
|---|---|---:|
| `is_repeat_customer` | `order_count >= 2` | 2,801 |
| `has_late_delivery` | `late_delivery_ratio > 0` (`late_delivery_ratio` が NULL なら NULL) | 6,498 (NULL 8) |

- 2 つのフラグは**独立して持つ**。両方に当てはまる顧客 (303 人) もいるため、優先順位を付けて 1 つのグループに入れることはしない。
- フラグは、当面は notebook の中で作る。

### 2. クラスタリングの対象

**どちらのフラグにも当てはまらない顧客**だけをクラスタリングする。フラグに当てはまる顧客にはクラスタを付けず、フラグで説明する。

| | 人数 |
|---|---:|
| 全顧客 | 93,358 |
| − リピーターまたは遅延経験者 (2,801 + 6,498 − 両方に当てはまる 303) | − 8,996 |
| − 遅れの有無が不明 (`has_late_delivery` が NULL。リピーターとは重ならない) | − 8 |
| = クラスタリングの対象 | 84,354 |
| − 入力する特徴量に NULL がある顧客 ([009](009_clustering_preprocessing.md)。レビューがない顧客) | − 453 |
| = **学習に使う顧客** | **83,901** |

### 3. クラスタリングに使う特徴量

入力は連続値を中心にし、次の 2 つを試す。学習に使う顧客は、どちらも同じ 83,901 人にする (比較の条件をそろえるため)。

| 試行 | 入力する特徴量 | 判断したいこと |
|---|---|---|
| 1 | `total_items_amount` (log1p)、`days_since_last_purchase` | 金額と最近性だけで、意味のある顧客群が得られるか |
| 2 | 試行 1 ＋ `avg_review_score` | 満足度を加えると、顧客群がどう変わるか |

- 前処理は [009](009_clustering_preprocessing.md) のとおり (対数変換してから標準化。標準化の平均と標準偏差は、学習に使う顧客から計算する)。
- `item_count`・`credit_card_order_ratio`・`has_review_comment` は、クラスタリングの対象の顧客でも 0 / 1 に近い (`item_count` は 90% が 1、`credit_card_order_ratio` は 1 回購入のため 0 か 1、`has_review_comment` は真偽値) ため、入力から外し、クラスタの解釈に使う。

## 理由

- **ルールで説明できる違いを、K-means に探させる必要はない。** リピーターかどうか、遅れを経験したかどうかは、条件を書けば判定でき、業務上の意味もはっきりしている。
- **連続値のクラスタリングが、0 / 1 の値に引っぱられなくなる。** 単純な条件分けでは捉えにくい、金額や最近性などの傾向の違いを探せる。
- **遅延経験者を外すことで、レビューの特徴量が「遅れたかどうか」を表しにくくなる。** 遅延経験者のレビューの平均は低い (すべて遅れ 2.26 / 一部遅れ 3.23 / 遅れなし 4.29。[008](008_feature_selection.md))。
- **分析の目的と手法の対応を説明しやすい。** ルールで説明できる違いと、データから見つけたい違いを分けて示せる。

## 試行の結果を見るときの注意

- 今回の目的は、シルエット係数を最大にすることではなく、**購買行動として解釈できる顧客群を見つけること**。
- 試行 1 は特徴量が 2 つのため、金額と最近性の組み合わせで分かれるかを確かめることになる。
- `avg_review_score` は 5 段階の値で、クラスタリングの対象の顧客の 62% が 5 である。標準化しても、この偏りはなくならない。
- 試行 2 でクラスタが変わっても、それだけでレビューが有益とは判断しない。クラスタの人数・中心・シルエット係数に加えて、金額・最近性による違いが残っているかを確認する。
- レビューは配送の体験を反映している可能性があるため、レビューを使った結果がどのような顧客像になるかを確認する。

## 影響

- [008](008_feature_selection.md) の「採用」の 8 つのうち、クラスタリングに入力するのは 2〜3 つになる。`order_count`・`late_delivery_ratio` はフラグの条件に、`item_count`・`credit_card_order_ratio`・`has_review_comment` はクラスタの解釈に使う。
- [009](009_clustering_preprocessing.md) の前処理の方針は、そのまま引き継ぐ。
- フラグに当てはまる顧客 (8,996 人)、遅れの有無が不明な顧客 (8 人)、レビューがない顧客 (453 人) には、クラスタが付かない。これらの扱いは、試行の結果を見てから決める。

## 見直す条件

- 試行 1・2 のどちらでも、購買行動として解釈できる顧客群が得られなかった → クラスタ数や、K-means 以外の手法 (連続値とカテゴリ値を両方扱える手法など) を検討する
- フラグを、ほかの分析やレポートでも使うことになった → mart の列にすることを検討する
- ルールで分ける顧客特性を追加したくなった (例: 複数商品の購入) → フラグの定義を見直す
