# 002. BigQuery の層構成

- 日付: 2026-10-08
- ステータス: 決定

## 背景

[001](001_table_selection.md) で選んだ 7 テーブルを BigQuery に取り込み、顧客セグメンテーション用のデータを作る。

CSV を取り込んで SQL を 1 本書くだけでも目的は果たせるが、それでは次の問題がある。

- 型の変換、重複の排除、集約といった性質の違う処理が 1 つの SQL に混ざり、どこで何をしているか追いにくい
- 分析の目的が変わったとき、元データに近い状態から作り直せない

そこで、処理の性質ごとに層を分ける。

## 決定

raw → staging → mart の 3 層に分け、層ごとに BigQuery のデータセットを分ける。

```
Olist CSV (ローカル)
   ↓ 読み込みスクリプト
raw      : CSV をそのまま
   ↓
staging  : 型・列名・表記を整える
   ↓
mart     : 分析の目的に合わせて結合・集約する
   ↓
顧客セグメンテーション
```

### 各層の責務

| 層 | やること | やらないこと | 粒度 | 作り方 |
|---|---|---|---|---|
| raw | CSV をそのまま入れる (全列 STRING) | 変換・修正 | CSV と同じ | テーブル (読み込み) |
| staging | 型の変換、列名の修正、表記をそろえる | 行の除外、結合、集約 | raw と 1:1 | ビュー |
| mart | 結合、集約、行の除外、重複の排除、特徴量の計算 | - | テーブルごとに明示する | テーブル |

#### raw

- 全列を STRING として読み込む。スキーマの自動検出は使わない。
  - 自動検出では郵便番号が数値になり、先頭の 0 が消える ([data_notes.md](../data_notes.md) を参照)。
  - 型の変換は staging で行い、変換に失敗する値があっても読み込みは止めない。

#### staging

- **元データの行はすべて残す。** 行を除くことは、分析の目的に依存する判断であり、staging では行わない。
  - 例: キャンセルされた注文を staging で除くと、キャンセル率を分析したくなったときに元に戻せない。
- やることの例
  - 日時の列を `TIMESTAMP` に変換する
  - 元データのスペルミスを直す (`product_name_lenght` → `product_name_length`)
  - 使わない列を落とす

#### mart

判断が入る処理 (行の除外、重複の排除など) はすべてここで行い、各テーブルの粒度を明示する。
セグメンテーション用に、粒度の異なる 2 つのテーブルを作る。

| テーブル (仮) | 粒度 | 内容 |
|---|---|---|
| 注文単位のテーブル | 1 行 = 1 注文 | 注文の金額・支払い・配送・レビューをまとめる。`order_reviews` を注文ごとに 1 件へそろえる処理はここで行う |
| 顧客単位のテーブル | 1 行 = 1 人 (`customer_unique_id`) | 注文単位のテーブルを集約した特徴量。セグメンテーションの入力 |

注文単位のテーブルを経由するのは、SQL を読みやすくし、途中の結果を検証できるようにするためである。

## 検討した代替案

### Cloud Storage にファイルを置き、データレイクとして扱う

```
Olist CSV → Cloud Storage → BigQuery raw → staging → mart
```

元のファイルをクラウド上に保管でき、BigQuery 側を作り直してもそこから再現できる。

今回は採用しない。

- Olist のデータは更新されない静的なデータセットであり、元ファイルはローカルと Kaggle から再取得できる
- バケットの作成・権限設定など、目的 (顧客セグメンテーション) に直接関係しない作業が増える

このため、raw 層は「データレイク」ではなく「元データをそのまま取り込んだ層」と位置付ける。

### mart を 1 つのテーブルにする

顧客単位のテーブルだけを作り、注文の集計もその中で行う案。テーブルの数は減るが、1 つの SQL が大きくなり、注文単位での検証ができなくなるため採用しない。

## 影響

- 読み込み (CSV → raw) は、変換ツールの外で、スクリプトで行う。
- `order_reviews` の重複の扱いなど、[data_notes.md](../data_notes.md) で「方針は未定」とした処理は、mart を作る段階で決める。

## 見直す条件

- データが定期的に更新されるようになり、取り込みの履歴を残す必要が出た → Cloud Storage を追加する
- 複数の mart で同じ中間処理を使い回すようになった → staging と mart の間に中間層 (intermediate) を追加する
