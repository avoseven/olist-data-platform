# 003. 変換ツールに dbt を使う

- 日付: 2026-10-08
- ステータス: 決定

## 背景

[002](002_layer_architecture.md) で決めた staging と mart を、BigQuery 上の SQL で作る。
SQL をどう管理し、どう実行するかを決める。

## 決定

**dbt Core** (`dbt-bigquery`) を使う。

- uv の環境に Python パッケージとして追加し、ローカルから実行する
- raw 層は dbt の外で読み込み、dbt からは source として参照する
- staging と mart を dbt のモデルとして作る

## 理由

- **層の依存関係を管理できる。** モデル同士を `ref()` でつなぐと、dbt が実行順序を決める。staging → mart の流れがコードに現れる。
- **データのテストを書ける。** 主キーの一意性 (`unique`, `not_null`)、参照整合性 (`relationships`) などを、モデルの定義と一緒に書ける。
  [src/check_relationships.py](../../src/check_relationships.py) で確認した内容を、パイプラインの一部として毎回検証できる。
- **ドキュメントと系譜を生成できる。** `dbt docs` で、列の説明やテーブル同士のつながり (リネージ) を確認できる。
- データ基盤の構築で広く使われているツールであり、このプロジェクトを通じて使い方を身につけたい。

## 検討した代替案

### SQL ファイルとスクリプト

`sql/` に SQL を置き、`bq` コマンドで順に実行する案。仕組みが単純で、覚えることが少ない。
ただし、実行順序・テスト・ドキュメントを自分で作る必要があり、それらは dbt が標準で備えているため採用しない。

### Dataform

BigQuery に組み込まれた変換ツールで、dbt とほぼ同じことができ、追加の環境構築も要らない。
GCP に依存した構成になること、dbt のほうが利用例や情報が多いことから、今回は dbt を選ぶ。

### dbt Cloud

dbt の実行環境を提供するサービス。今回は個人のプロジェクトで、ローカルからの実行で足りるため、dbt Core を使う。

## 影響

- dbt を学ぶ時間が必要になる。
- `sql/` ディレクトリは使わず、SQL は dbt のプロジェクトに置く (置き場所は環境構築の際に決める)。
- `src/check_relationships.py` の検証の多くは、dbt のテストに移せる。
  スクリプトは、初期調査の記録として残す。
